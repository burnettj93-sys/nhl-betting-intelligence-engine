## Copy verification procedure (checksums + row counts)

Checksums alone confirm bytes transferred correctly; row counts confirm the copy is a real, queryable database and not a truncated/corrupted file that happens to share a prefix. Do both.

1. **Before copying**, on the source (local Mac), record checksum + a real table row count for each CRITICAL database:
   ```bash
   sqlite3 nhl.db "SELECT COUNT(*) FROM games;"
   sqlite3 operational/prospective_observations.db "SELECT COUNT(*) FROM predictions;"
   sqlite3 operational/paper_bankroll.db "SELECT COUNT(*) FROM paper_bets;"
   ```
   (Table names per `docs/BACKUP_AND_RESTORE.md`'s own real verification run, which used this exact pattern: `original games: 1113 | restored games: 1113`.)
2. **Copy** via `scp`/`rsync` directly (never through `git`, these are gitignored on purpose) to a **new, isolated path** on the VPS first -- never straight into the path the app will read from.
3. **After copying**, re-run the same checksum and row-count commands against the copy. Checksum mismatch or row-count mismatch means the copy is not trustworthy -- do not proceed; re-copy.
4. **Only once verified**, move the checked copy into its real production path (per `docs/VPS_PRODUCTION_LAYOUT.md`, that's `/opt/nhl-engine/data/...`) and let `deploy/provision_layout.sh` (or a manual symlink, if it already ran) make it visible at the path the app expects.

This mirrors `docs/BACKUP_AND_RESTORE.md`'s own already-proven restore procedure exactly (restore to a new path, verify, only then promote) -- no new verification philosophy invented for this block.

## What never needs to move

`*_cache.json` files (ingestion health, data readiness, odds/moneyline/sweep caches) -- temporary, regenerated by the next real run on the VPS, explicitly never backed up per `docs/BACKUP_AND_RESTORE.md`. Letting the VPS start with none is the correct, honest state (matches a fresh local-Mac checkout's own state before its first real run).
