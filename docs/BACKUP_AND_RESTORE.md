# Backup and Restore

**Date:** 2026-09-24. **Job:** `com.nhlengine.database-backup`, installed and loaded, runs daily at 07:45 (after sync/settlement/post-mortem). **Script:** `operational/backup_databases.py`. **Method:** SQLite's own online backup API (`Connection.backup()`), not a raw file copy — safe to run against a database another process is actively writing to (a raw copy of a live SQLite file, especially in WAL mode, can capture it mid-write and produce a corrupt backup).

## Classification

| Database | Class | Why | Regeneration if lost anyway |
|---|---|---|---|
| `nhl.db` | **CRITICAL/BACKUP** | Real, accumulating game/roster data. Technically re-fetchable from the NHL's public API — but a live daily sync's `observed_at_utc` reflects the real moment this system learned each fact, which is the core "what did we know when" guarantee this whole platform is built around. A backfill run today would stamp a different, later knowledge-time, permanently losing that real historical detail. | Re-run `python3 -m ingest.nhl_api` ingestion for the needed range — but loses real point-in-time knowledge-time fidelity for anything captured live. |
| `operational/prospective_observations.db` | **CRITICAL/BACKUP** | Every real prediction snapshot ever made, immutable by design. Zero source of truth exists anywhere else. | None — this is the only copy of real prediction history that will ever exist. |
| `operational/paper_bankroll.db` | **CRITICAL/BACKUP** | Real paper-bet history and bankroll state. | None — not reconstructible. |
| `operational/auth_store.db` | **CRITICAL/BACKUP** | Real user accounts (usernames, hashed passwords, roles). | Not reconstructible, but recoverable in a *different* sense: the app's own bootstrap flow (`dashboard/auth.py::render_bootstrap_admin_form`) will recreate an admin account from scratch if this file is lost — inconvenient (every friend re-added manually), not catastrophic. |
| `research/real_nhl_pbp/research_pbp.db` | **REPRODUCIBLE/OPTIONAL** | Already gitignored, already documented as regenerable. | `research/real_nhl_pbp/`'s own ingestion scripts, from the still-gitignored raw JSON. |
| `research/moneypuck_ingestion/research_moneypuck.db` | **REPRODUCIBLE/OPTIONAL** | Same. | `research/moneypuck_ingestion/ingest_moneypuck_team.py`. |
| `operational/special_teams_history.db` | **REPRODUCIBLE/OPTIONAL** | Same (per the 2026-08-30 freeze manifest). | `python3 -m operational.backfill_special_teams_history`. |
| `fantasy/storage/fantasy_store.db` | **REPRODUCIBLE/OPTIONAL** | Post-2026-09-24 compliance rebuild, this file holds only `user_selection`/`fantasy_recommendations`/`watchlist` — low-value app preferences, not irreplaceable data. | Re-select your league/team; recommendation history and watchlist are the only real loss, both low-stakes. |
| `fantasy/storage/yahoo_token.enc` | Backed up implicitly (small, encrypted) but **not in `CRITICAL_DATABASES`** — it's a single encrypted file, not a SQLite database. | Losing it just means redoing the interactive Yahoo consent once. | Re-run the Yahoo connection flow (`35_Fantasy_Settings.py`). |
| `*_cache.json` (ingestion health, data readiness, odds/moneyline/sweep caches) | **TEMPORARY — never backed up** | Regenerated by their own job on every single run. | Just let the next scheduled run recreate them. |

## What the job actually does

1. For each of the four CRITICAL databases, runs `Connection.backup()` into `operational/backups/<name>/<name>_<UTC timestamp>.db`.
2. A missing source database is `SKIPPED`, not a failure (e.g. before the first real prediction is ever recorded, `prospective_observations.db` doesn't exist yet).
3. Keeps the most recent 14 backups per database, deleting older ones (roughly two weeks at a daily cadence).
4. A failed backup never leaves a partial/corrupt file behind — it's deleted immediately on any exception.
5. Records its own outcome via `operational/ingestion_health.py` under the `database_backups` component, visible on the Data Status page's "Scheduled ingestion job health" section and in `opening_day_readiness.py`'s output.

## How to restore, for real, if it's ever needed

**This never happens automatically — restoring is always a deliberate, explicit action.**

1. Find the backup you want: `ls operational/backups/<name>/` (sorted by timestamp in the filename).
2. Restore it to a **new** path first, never directly over the live database:
   ```python
   from operational.backup_databases import restore_from_backup
   from pathlib import Path
   restore_from_backup(Path("operational/backups/nhl_db/nhl_db_20260924T152313Z.db"), Path("/tmp/nhl_restored_check.db"))
   ```
3. Inspect the restored copy (open it, spot-check row counts / recent rows) before doing anything else.
4. Only once you're satisfied, stop any scheduled job that writes to the real database (`launchctl unload ~/Library/LaunchAgents/com.nhlengine.<relevant-job>.plist`), move the real file aside (`mv nhl.db nhl.db.pre-restore`), copy the verified restored file into place, then reload the job.

## Recommendation: an off-box copy

Everything above protects against local corruption or an accidental `rm`, but all 14 rotated backups still live on the same machine as the originals — a real disk failure or laptop loss takes both. Given the small size of these four databases, a simple weekly `rsync`/cloud-storage sync of `operational/backups/` to a second location (another machine, or any cloud storage you already use) would close that gap cheaply. **Not implemented in this pass** — a deliberate decision for you to make, not assumed.
