# Cloud Live-Data Architecture

2026-09-25, Cloud live-data sprint. Follows `docs/STREAMLIT_MEMORY_CERTIFICATION.md`: the Community Cloud app is a thin, read-only presentation layer, but its data was **frozen** (a `board.json` regenerated by hand and committed to `master`). This sprint makes it display **fresh** betting intelligence automatically, without loading models in Streamlit, running anything in Streamlit, committing data to `master`, or adding a paid provider.

```
 LOCAL ENGINE (laptop / VPS)                                        STREAMLIT COMMUNITY CLOUD
 NHL sync · Odds API · models · recommendations                     read-only · no models · no schedulers
 paper bets · settlement · post-mortem · health
        │  successful job                                                      ▲
        ▼                                                                      │ HTTPS GET (cached 180 s)
 operational.publish_cloud_snapshot ──build (read-only)──validate──►  cloud-data branch  ──► raw.githubusercontent.com
        │                  hash unchanged? ⇒ NO_CHANGE (no commit)     current/snapshot.json          (last-known-good in memory)
        └── isolated temp clone · atomic write · one ref update        current/metadata.json
```

## Chosen transport: a dedicated `cloud-data` git branch

Audit of the free options (scored against the requested criteria; facts about this repo: `origin` is a **public** GitHub repo, and `gh` is already authenticated with `repo` scope):

| Option | Update reliability | Auth to publish | Reader access | Rate limits / latency | History growth | Atomic | Rollback | Verdict |
|---|---|---|---|---|---|---|---|---|
| **A. `cloud-data` branch** (`raw.githubusercontent.com`) | one `git push`; retryable | existing git/`gh` credentials, no new secret | plain HTTPS GET, no token, no API quota | CDN, ~1 MB (≈100 KB gzip); GitHub caches raw ~5 min | bounded by design (below) | single-ref push = atomic | `git revert` / reset the branch | **chosen** |
| B. GitHub Release asset / Actions artifact | needs API + token juggling; artifacts expire; asset replace is delete-then-upload (a window with nothing served) | token with release scope | release assets need redirect handling; artifacts need auth even for public repos | API rate limits apply | assets accumulate or are replaced non-atomically | no | awkward | rejected |
| C. Secret gist | `gh gist edit`; unofficial "secret" is just an unguessable URL | `gist` scope (available) | raw gist URL, no token | CDN | gist keeps full revision history (unbounded, not squashable) | yes | gist revisions | rejected: unbounded history, security-through-obscurity, second system to manage |
| D. Other free static hosting | would add a new provider/account | new credentials | fine | fine | n/a | varies | varies | rejected: violates "no new provider" |

Option A wins on simplicity and robustness: no new credential, no new service, an atomic update primitive, and trivial rollback. Its costs are documented rather than hidden:

- **GitHub's raw CDN caches ~5 minutes**, so end-to-end latency is *engine publish → up to ~5 min CDN → up to 3 min reader TTL*. Acceptable for a moneyline board that refreshes a few times a day.
- **Public exposure** (see Security & privacy).

### Branch contents and history strategy

The branch contains **only** `README.md`, `current/snapshot.json`, `current/metadata.json` — never source code, raw API responses, odds captures, databases, logs or corpora (those live in the operational archive and backups).

- Each publication is one small commit (`cloud-data #<seq> <hash8> data_as_of=<ts>`).
- **Bounded history:** every `HISTORY_RESET_EVERY` (=50th) publication replaces the branch with a fresh orphan commit (`--force-with-lease` against the previous tip). The branch therefore holds at most ~50 recent snapshots — enough to debug or roll back — and never grows forever. Replaced commits become unreachable and are garbage-collected by GitHub.
- The publisher clones the branch **shallow (depth 1)** into a temp directory each time, so the cost of history never reaches the publisher either.

## Snapshot schema (`schema_version` 2)

Defined in `operational/cloud_snapshot_schema.py` (stdlib only, shared by publisher and reader). `schema_version` 1 is the bundled `board.json` from the memory sprint and is still *readable*, used only as the emergency/bootstrap fallback.

| Section | Contents | Provenance label |
|---|---|---|
| `metadata` | `schema_version`, `generated_at`, `generated_by`, `source_master_commit`, `engine_mode`, `data_as_of`, `freshness{nhl_data, odds, recommendations, settlement, postmortem}`, `sections_omitted`, `provenance`, plus (added at publication) `content_hash`, `publication_seq` | — |
| `demo` | the deterministic demo board (games, roster, goalies, opportunities, prop opportunities, goalie-saves, market movement, per-player history/activity, Team SOG projections). Copied from the git-bundled `board.json` (a test proves it equals a live recompute), so publishing never builds the ~430 MB model stack. Every row is stamped `source`/`is_demo` | `SIMULATED — DEMO ONLY` |
| `live_moneyline_rows` | real DraftKings moneyline vs the engine's Elo model (model P, edge, EV, decision, `captured_at_utc`) | `LIVE — DRAFTKINGS` |
| `real_recommendations` | recommendations the engine recorded in its ledger against real prices (MONEYLINE + props), real-market Game Edge Parlays | `REAL MARKET` |
| `performance` | paper-bankroll summary/breakdowns/bets per track (last 200 bets per track) | — |
| `morning_review` | the post-mortem the engine computed | — |
| `model_learning` | the daily model review (recent model performance) | — |
| `ledger` | ledger summary + last 100 rows per record type | — |
| `data_status` | readiness cache + ingestion-job health | — |
| `health` | the engine's system-health pills + production summary + odds status | — |

Real and demo data are **never merged into one unlabeled structure**: separate sections, separate labels, and the labels are the project's canonical strings (`LIVE — DRAFTKINGS`, `SIMULATED — DEMO ONLY`, `REAL MARKET`). Size: ~680 KB compact JSON (~100 KB gzipped on the wire).

Not in the snapshot, by construction: model internals, raw API responses, credentials, user/account data, session state, Yahoo anything.

### Fix delivered with this sprint: live rows were silently frozen
`dashboard/live_dk.py` only read *per-event* archive captures; the scheduled moneyline pulls archive a *sport-level list* response, which it skipped. "Live Model Edges" therefore stopped at the last per-event probe (2026-09-15) even locally while fresh captures piled up. It now reads both shapes (33 events, newest 2026-09-25 vs 20 events, 2026-09-15). All rows are still `WAIT` because the pre-existing Elo-staleness safety gate downgrades them (Elo ratings run through 2026-04-16) — that safety is unchanged.

## Freshness (factual only) — two separate questions

A snapshot published one minute ago can still carry a sportsbook price captured hours ago. So freshness is judged at **two levels that are never conflated**:

### 1. SNAPSHOT / system freshness (broad, daily-cadence data)

`classify_freshness(metadata.data_as_of)`, where `data_as_of` is the newest of the real odds capture and the newest recorded recommendation (falling back to the NHL sync time). This is the overall health concept and the right yardstick for **general data: Morning Review, settlement, post-mortem, Ledger, Paper Performance, Data Status**, which are produced on a daily cadence.

| State | Age of `data_as_of` |
|---|---|
| `CURRENT` | ≤ 13 h |
| `STALE` | ≤ 36 h |
| `VERY_STALE` | > 36 h |
| `UNAVAILABLE` | missing, unparseable, or in the future — never presented as fresh |

### 2. MARKET / RECOMMENDATION freshness (strict, per price)

`classify_market_freshness()` / `recommendation_freshness()` / `parlay_freshness()` in `operational/cloud_snapshot_schema.py`. Applies to **odds, model edges, recorded recommendations and Game Edge Parlays**. The clock is the price's own capture time (`odds_captured_at_utc` / `captured_at_utc`; the recommendation's `created_at_utc` only if no price time exists) — never the snapshot's `generated_at`.

| Situation | CURRENT if price age is | Otherwise |
|---|---|---|
| Ordinary market | ≤ 3 h (180 min) | `STALE` (`OLDER_THAN_3H`) |
| Game starts within 4 h | ≤ 90 min | `STALE` (`NEAR_GAME_OLDER_THAN_90M`) |
| Game already started | never | `STALE` (`GAME_STARTED`) |
| No / unparseable price time, price time in the future, or price time later than the snapshot that claims to contain it (impossible/misleading) | never | `UNAVAILABLE` |

Rules that follow from this:
- The displayed state is the **stricter** of the market state and the snapshot state, so a stale snapshot can only make a price stricter, and a fresh snapshot can never make an old price look current.
- Each recommendation/market card exposes **created_at**, **price captured at**, **game start** and the **freshness classification** (with age and reason).
- **Game Edge Parlays inherit the stalest leg.** One stale leg ⇒ the parlay is titled "Game Edge Parlay — STALE (not a current opportunity)", with the limiting leg shown.
- **Presentation only.** `decision_policy`, `prospective_status` and every stored recommendation are untouched. A non-CURRENT row simply shows `STALE` in place of its actionable badge ("Shown as" column) while the recorded action remains visible.
- The banner shows `MARKET FRESHNESS (separate from snapshot freshness)` next to DATA AS OF / LAST UPDATED. Its headline now reads "SNAPSHOT CURRENT (odds freshness is judged separately)".
- Applies in LOCAL as well as Cloud mode (a three-day-old price is not live anywhere). Morning Review and other daily data are *not* subject to the 3 h / 90 min odds rule.

The UI always shows **DATA AS OF** and **LAST UPDATED** (`generated_at`) plus per-component timestamps. Nothing is invented: if the laptop sleeps, timestamps stop advancing and the states degrade honestly. Note the publisher runs after the 4×/day odds pulls, so between pulls prices legitimately age past 3 h (and past 90 min near a game) — that is the intended, honest outcome; more frequent pulls near game time are what keep them CURRENT.

### Stale-data behavior
- Banner turns amber (`DATA STALE — … do not treat it as live`) or red (`VERY STALE`, `UNAVAILABLE`) on **every** page when the *snapshot* is stale.
- "Live Model Edges" becomes "Model Edges — ODDS STALE (not live)" when no price is CURRENT; the `LIVE — DRAFTKINGS` label becomes `STALE — LIVE — DRAFTKINGS (NOT CURRENT)` when the snapshot is not CURRENT; each non-CURRENT row's badge is replaced by `STALE`.
- Recorded recommendations carry Price captured / Game start / Market freshness columns and a "Shown as" column.

## Publication

```
python3 -m operational.publish_cloud_snapshot            # build → validate → publish if changed
python3 -m operational.publish_cloud_snapshot --dry-run  # build + validate only
python3 -m operational.publish_cloud_snapshot --output f # write a validated file (no git)
python3 -m operational.publish_cloud_snapshot --force    # ignore NO_CHANGE / rate limit
```
Statuses: `SUCCESS`, `PARTIAL_SUCCESS` (published, but an optional section failed to build and was omitted — listed in `sections_omitted`), `NO_CHANGE`, `DEFERRED` (rate-limited / another publish running), `FAILED` (nothing published). Exit code 0 unless `FAILED`.

- **Read-only build** (`operational/cloud_snapshot_builder.py`): databases opened `mode=ro` or replaced by an empty in-memory schema; no bets, no observations, no network, no models, and the Yahoo token store is never touched. Each section is isolated — one failure omits that section only.
- **Atomic:** serialize → re-parse the exact bytes → validate → write temp file → `os.replace` into place inside an isolated clone → one `git push`. A partially written snapshot can never be published; a failed write leaves the previous file intact.
- **Idempotent (`NO_CHANGE`):** `content_hash` = sha256 of the canonical document with publication-only metadata (`generated_at`, `generated_by`, `source_master_commit`, `content_hash`, `publication_seq`) and compute-time stamps removed. Unchanged local state ⇒ `NO_CHANGE` with **no network call**; lost local state ⇒ compared against the remote's `metadata.json` ⇒ still `NO_CHANGE`, **no commit**.
- **The live checkout is never switched.** All git work happens in a throwaway temp clone; publishing cannot disturb the running schedulers.
- **Bounded retries/backoff:** 3 attempts, 2 s / 6 s backoff, 60 s per git call; a minimum 120 s between real pushes; a lock file prevents overlapping publishes.
- **Credentials:** whatever git already uses for `origin` (the `gh` credential helper). Nothing is hard-coded and nothing is put in the snapshot.

### Triggers (integrated into existing jobs; no new scheduled job)
`operational/cloud_publish_hook.py::publish_after()` is called at the end of:

| Job | When |
|---|---|
| `live_odds_daily_pull` `--mode=moneyline`, `props`, `sweep-first`, `sweep-second` | only after a real successful refresh (`ran: true`) |
| `settle_daily_observations` | after a successful settlement run |
| `daily_postmortem` | after the post-mortem is written |

**Not** the 30-minute pregame NHL refresh. Because unchanged content is `NO_CHANGE`, a trigger that produced nothing new costs one local build (~3 s) and no git activity.

**Automatic publishing is OFF by default.** Set `NHL_ENGINE_CLOUD_PUBLISH=ON` in `.env` (or the environment) to enable it; a manual `python3 -m operational.publish_cloud_snapshot` always works. The hook runs the publisher in a **subprocess with a 240 s timeout**, skips on a STANDBY machine, and never raises: **publication failure cannot break or roll back the engine** (tested). It shows up as `DEGRADED` / `ERROR` in health.

### Health
`system_health.cloud_snapshot_publish_health()` (component `cloud_snapshot_publish` in `ingestion_health`): last attempt, last success, status, snapshot age, last error. `NOT_REQUIRED` (opt-in and never run) · `WAITING` · `OK` (≤ 36 h since a success; `NO_CHANGE` counts) · `DEGRADED` (latest attempt failed, recent success exists) · `STALE` · `ERROR` (never succeeded). Surfaced in `production_health_summary()` (`CLOUD_SNAPSHOT`), the health snapshot, the Data Status page and the published `health` section.

## The Cloud reader (`dashboard/snapshot_source.py`)

Stdlib-only; imports no research/model code (tested in a clean process). In `COMMUNITY_CLOUD_MODE` (or `NHL_ENGINE_SNAPSHOT_SOURCE=REMOTE`):

- `GET` with an 8 s timeout, ≤ 2 attempts (transient errors only; a 4xx is not retried), 0.5 s backoff, 8 MB cap, then schema validation. Corrupt JSON, unsupported schema, missing fields, oversize ⇒ **rejected**; a rejected document never replaces a good one and is never displayed.
- **Cache:** one entry, **TTL 180 s** (within the requested 2–5 min); a failed fetch backs off 30 s; a stampede of sessions causes one fetch (tested). Streamlit reruns never hit GitHub.
- **Last-known-good:** on a failed refresh the last good snapshot in process memory is kept and labeled `REMOTE UPDATE FAILED (<error>)` with its own `DATA AS OF`; it is never treated as fresh.
- **Fallback:** if no remote snapshot ever loaded, the git-bundled `board.json` is used, labeled `BUNDLED_FALLBACK`, and (being old) classifies `VERY_STALE`.
- Source label states: `REMOTE`, `REMOTE_LAST_KNOWN_GOOD`, `BUNDLED_FALLBACK`, `NONE`.
- Config (all optional): `NHL_ENGINE_SNAPSHOT_SOURCE` (`REMOTE`|`BUNDLED`), `NHL_ENGINE_SNAPSHOT_URL` (default: this repo's `cloud-data/current/snapshot.json` raw URL), `NHL_ENGINE_SNAPSHOT_TOKEN` (only if the source is later made private; sent as an `Authorization` header, never logged or displayed).
- ADMIN Diagnostics shows: snapshot source, remote fetch status, last successful fetch, last attempt, snapshot `generated_at`, `data_as_of`, data age, schema version, content hash, cache TTL, last error — never a token or query string.

## Security & privacy

**What is published.** Shared betting data only: recommendations, odds/edges, performance, health. Enforced *before* publication by `validate_snapshot(for_publication=True)`, on the exact bytes to be pushed:

- JSON strict (no NaN/Infinity), schema and timestamps valid;
- no key that looks like a credential (`api_key`, `token`, `password`, `secret`, `authorization`, `client_id/secret`, …);
- no credential-shaped value (GitHub/`sk-`/AWS tokens, `Bearer …`, private-key blocks, `?api_key=` URLs);
- **the value of any configured secret** (Odds API key, Yahoo client/secret/encryption key, setup code, snapshot token) appearing anywhere;
- no absolute filesystem path (builder also relativizes repo paths);
- **structurally no Yahoo content**: any key or value containing "yahoo" fails validation, and the builder never reads Yahoo storage;
- no user/account/session data (there is none in any source section).

**Is the raw snapshot public?** Yes — the repository is public, so `cloud-data` is world-readable, exactly like `board.json` on `master` already is. The snapshot contains no secret, no Yahoo data and no personal data; what it *does* expose is the engine's current betting picks and paper performance. Tradeoffs:

| Choice | Complexity | Exposure |
|---|---|---|
| **Public branch (implemented)** | lowest; no secret on Cloud | anyone can read current picks, bypassing the Streamlit viewer allow-list |
| Private data repo + read-only token in Cloud secrets | one extra repo + a fine-grained PAT (Contents: read) | private; the reader already supports it (`NHL_ENGINE_SNAPSHOT_TOKEN` + `NHL_ENGINE_SNAPSHOT_URL`) — a later, owner-approved change (creating a repo is an owner action) |

Recommendation: ship public (it changes no exposure the repo doesn't already have and the paper-only picks are not sensitive), and move to the private-repo option if the owner later decides current picks should not be world-readable.

## Authentication in COMMUNITY_CLOUD_MODE

> **Superseded 2026-09-26:** Community Cloud has no application-level authentication. Streamlit private sharing is the only access gate; the platform-viewer / ADMIN-email / setup-code mechanism described below was removed (Community Cloud does not supply `st.user.email`, and the ephemeral filesystem cannot hold accounts). The text below is historical.

Community Cloud's filesystem is ephemeral, so custom accounts cannot be relied on for friend identity. Cloud mode therefore uses the **platform's private-viewer gate** as the primary access control, with the app enforcing ADMIN-only pages itself. LOCAL/PRODUCTION auth is unchanged.

1. **Platform viewer identity (opt-in).** If the owner sets the secret `NHL_ENGINE_TRUST_PLATFORM_VIEWER=ON` — an explicit declaration that the app is restricted to an invited viewer list in Streamlit's Sharing settings — the signed-in viewer's platform email is the identity: `ADMIN` if it is in the secret `NHL_ENGINE_ADMIN_EMAILS` (comma-separated), otherwise `USER`. No login form appears. The app cannot verify from the inside that the platform gate is on, so nothing is trusted without that declaration; with no email present it falls back to the custom gate. **It never mints ADMIN unless the email is listed.**
2. **ADMIN bootstrap** (the fallback and the only other way to get ADMIN): requires the secret `NHL_ENGINE_ADMIN_SETUP_CODE`; with none configured no account can be created, so the first anonymous visitor can never become ADMIN. The code is compared in constant time and never rendered or logged (tested).
3. **Roles.** `USER` sees the betting pages (Today, Games, Game Detail, Player/Team Intelligence, Player Props, Goalies, Combinations, Market Movement, Model Health/Learning, Paper Performance, Ledger). `USER` cannot reach **Diagnostics, Morning Review, Data Status** (operational surfaces: ADMIN-only in Cloud mode, unchanged locally), Yahoo/Fantasy (not registered in Cloud at all), or any admin function — enforced by both the page registry and `auth.require_admin()` inside each page (server-side).

**Limitations, stated plainly**
- If the owner did not enable the Sharing allow-list, the app is public: only ADMIN-gated data is protected, and anyone can read the betting pages **only if** they pass the custom login — which, with no accounts on ephemeral storage, means nobody can. In practice the allow-list (with the trust flag) is required for friends to get in.
- I could not verify from here exactly which `st.user` fields Community Cloud populates for viewers, nor the plan limits on private apps; the code reads `email` defensively and the runbook includes a check to perform once deployed.
- Custom accounts still vanish on restart; that is why platform identity is the design for Cloud.

## Failure handling matrix

| Failure | Behavior |
|---|---|
| Publisher: validation fails | `FAILED` / `VALIDATION: …`; nothing pushed; engine unaffected |
| Publisher: git/network down | 3 bounded attempts, then `FAILED`; engine unaffected; health `DEGRADED` |
| Publisher: a section fails to build | `PARTIAL_SUCCESS`; section omitted and listed |
| Publisher: crash / hang | caught (never raises); subprocess hard timeout 240 s |
| Publisher: concurrent run | `DEFERRED` |
| Reader: remote unreachable / 4xx / 5xx / timeout | last-known-good labeled `REMOTE UPDATE FAILED`; else bundled fallback labeled |
| Reader: corrupt / wrong schema / oversize | rejected; good snapshot kept |
| Laptop asleep / engine stopped | `data_as_of` stops advancing → `STALE` → `VERY_STALE` (factual) |
| Snapshot lacks a section (e.g. bundled fallback) | that page says so; nothing is faked |

## Rollback

- **Bad snapshot published:** `git revert` the latest commit on `cloud-data` (or force-push the previous good tip); the reader picks it up within ~8 minutes. Or point `NHL_ENGINE_SNAPSHOT_SOURCE=BUNDLED` in Cloud secrets to serve the bundled fallback immediately.
- **Disable publishing:** remove `NHL_ENGINE_CLOUD_PUBLISH` (or set it to `OFF`) — jobs immediately stop invoking the publisher; nothing else changes.
- **Remove the data branch:** `git push origin --delete cloud-data`; Cloud falls back to the bundled snapshot (labeled, `VERY_STALE`).
