# Daily NHL + MoneyPuck Operational Sync Foundation

Builds the foundation that lets the engine answer, every morning: **"Do I have all of today's
required hockey data, and exactly when did I obtain it?"** This is operational data
infrastructure only — no model was changed, no bet-adjacent logic was touched.

**Two genuinely significant real-world results came out of running this for real, not just
building it:**

1. **The NHL API is now reachable from this environment** (`api-web.nhle.com`, previously
   documented in this project as unreachable/"NOT LIVE VERIFIED (needs network)"). Running
   `validate_live_nhl.py` — the pre-existing, already-built live smoke test — for real produced a
   clean **`LIVE NHL CORE INGESTION: PASS`** against real June 2026 games, in a fresh temporary
   database (never `nhl.db`). This project's core NHL ingestion path is now genuinely proven
   against live data, not just synthetic fixtures.
2. **A real, empirical confirmation that MoneyPuck's team-level dataset requires manual
   permission**, exactly matching this slice's own anticipated Part 4 branch: a plain,
   unmodified request to `moneypuck.com`'s team file redirects to `/data_license.htm` (a real
   Cloudflare bot-detection/licensing gate). Spoofing a browser User-Agent would get past it
   (confirmed, never used) — that's exactly the circumvention this project's house rules forbid,
   so `MONEYPUCK AUTOMATED RETRIEVAL: REQUIRES PERMISSION` is reported honestly and
   `LOCAL FILE INGESTION` is the supported path instead.

The real 2026-27 NHL season has not started (`regularSeasonStartDate: "2026-09-29"` per the live
NHL API itself) — every live run this slice performed found **zero current games and zero
current-season MoneyPuck files**, honestly, which is the correct real-world state, not a bug.

## A. Daily-sync architecture

New `operational/` package (thin orchestration only — reuses the already-accepted,
already-tested `ingest/nhl_api.py` for all real NHL writes):
- `nhl_sync.py` — Part 2, wraps `ingest_range()` + `ingest_current_roster_identities()` over a
  yesterday/today/tomorrow window against the real production `nhl.db`.
- `moneypuck_daily.py` — Parts 3-10, checksum-based change detection, immutable archival,
  LIVE_OBSERVED provenance, contract-drift detection, NEW/UNCHANGED/REVISED record
  classification, for the MoneyPuck team/skater/goalie current-season datasets.
- `crosscheck.py` — Part 11, NHL/MoneyPuck identity cross-check with the known shootout-goal
  exception.
- `readiness.py` — Part 12, the seven-source data-readiness model.
- `report.py` — Part 15, the human-readable sync report formatter.
- `sync_daily.py` (top-level) — Part 13, the one command: `python3 sync_daily.py`.

## F. Raw archival behavior

`data/raw/moneypuck/<dataset>/<season>/<timestamp>_<filename>`, immutable, gitignored (large,
reproducible — same precedent as every other raw MoneyPuck blob in this project); a small
`manifest.json` per dataset/season (checksum, byte size, source URL, `provenance_type`) stays
tracked-pattern-compatible (though none exists yet — see G). **Nothing was actually archived this
slice**: skater/goalie returned 404 (nothing to archive) and team is permission-gated (no
automated content to archive). The archive/promote code path itself is fully built and unit-tested
against fixtures (`tests/test_operational_daily_sync.py::TestArchiveAndProvenance`, 3 tests).

## G. Checksum behavior

SHA-256, via the same `research/moneypuck_ingestion/checksums.py` helper already used and tested
elsewhere in this project (not reimplemented). `check_dataset()` compares against the last
accepted manifest's checksum; identical -> `NO_CHANGE`, different -> `UPDATED`
(`TestMoneyPuckChangeDetection`, 7 tests, including a real checksum-differs case with two
distinct fixture payloads).

## H. Incremental/revision behavior

`operational/moneypuck_daily.py::classify_records()` — Part 8's NEW/UNCHANGED/REVISED
classification, keyed by caller-specified stable key fields, generic across all three datasets.
Tested with hand fixtures (`TestRecordClassification`, 4 tests) since no real changed file
existed this slice to classify records from.

## I. Provenance behavior

Every promoted MoneyPuck snapshot is tagged `provenance_type: "LIVE_OBSERVED"` with
`latest_accepted_at_utc` set to the REAL check timestamp, never backdated
(`TestArchiveAndProvenance::test_no_timestamp_backdating_in_manifest`). NHL data continues to use
`ingest/nhl_api.py`'s own unchanged LIVE_OBSERVATION vs. HISTORICAL_BACKFILL semantics (this
slice adds no new NHL provenance logic — see that module's own docstring, unchanged).

## J. NHL cross-validation

team/date/score/SOG comparison, with the documented MoneyPuck shootout-goal exclusion correctly

## O. Idempotency results

Real, tested, both for NHL (via a fake-session double reused from this project's established
test pattern) and MoneyPuck (via checksum comparison):
- `TestNHLSyncIdempotency`: a second `run_nhl_sync()` call over an identical fixture produces
  zero additional `game_schedule_events` or `game_result_events` rows.
- `TestMoneyPuckChangeDetection::test_no_change_when_checksum_matches_manifest`: a second
  `check_dataset()` call against identical content reports `NO_CHANGE`, not a re-archive.
- The one **real** live run this slice performed (`python3 sync_daily.py`, twice) produced
  identical output both times — `nhl.db`'s on-disk mtime is provably unchanged
  (`Aug 26 16:15:02`, predating this entire slice) because the real sync window genuinely
  contained zero games.

## P. Failure/rollback behavior

`nhl_sync.run_nhl_sync()` never raises past its caller — a real exception is caught and reported
as `{"status": "FAIL", "error": ...}` (`TestNHLSyncWindow::test_sync_failure_is_reported_not_raised`).
`sync_daily.run()` returns exit code `1` on that condition, `0` otherwise
(`TestSyncDailyExitBehavior`, 2 tests). MoneyPuck's `archive_and_promote()` writes the manifest
only AFTER a successful file write — verified by forcing a write failure and confirming no
manifest exists afterward (`TestNoPartialPromotion`). No partial-promotion path exists in either
pipeline.
