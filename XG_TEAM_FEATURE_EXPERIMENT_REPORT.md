## A. Exact MoneyPuck fields used (Part 1 audit, read from source this turn)

Read directly from `research/moneypuck_ingestion/schema.sql` and
confirmed present via `PRAGMA table_info` against the real
`research_moneypuck.db` (52,480 rows, verified this turn): `xg_for` /
`xg_against` (MoneyPuck's `xGoalsFor`/`xGoalsAgainst`) at
`situation IN ('5on5', 'all')`. This experiment reads **only these two
columns**, at these two situations — no shot-attempt, danger-zone,
score-adjusted, or 5v4/4v5 field is used this slice (all present in the
schema and preserved in the data, per Part 4/26, but deliberately
untouched here to keep the feature family minimal). `5on4`/`4on5` rows
exist in the table and were left alone.

## B. Exact formulas for every derived feature

- **5v5 xG share** (`rolling_xg_share`, situation=`5on5`):
  `xGF / (xGF + xGA)`, summed over the most recent `window` season-scoped
  prior games, then divided — a rate in (0, 1).
- **All-situation xG differential per game** (`rolling_xg_diff_per_game`,
  situation=`all`): mean of `(xGF - xGA)` per game over the most recent
  `window` season-scoped prior games — a per-game rate, comparable
  regardless of games played.
- **xG form delta** (`xg_form_delta`, situation=`5on5`): the SAME metric
  (5v5 xG share) computed twice — once over the most recent
  `short_window` games, once over the most recent `long_window` games —
  and subtracted: `short_window_share - long_window_share`. Positive
  means a team is trending better than its own medium-term baseline
  right now, independent of whether that baseline itself is strong.

All three are computed **only** via
`research/moneypuck_ingestion/query.py::team_stats_as_of()` — no direct
SQL appears in `research/moneypuck_team_features.py`
(`tests/test_moneypuck_team_features.py::TestNoDirectSqlBypass` AST-scans
this and passes).

## C. Rolling windows tested

`{10, 25}` for the level features (5v5 xG share, all-situation xG diff) —
matching Part 22's example scale (short: 5-10, medium: 20-30), kept to
exactly 2 values per family per instruction. The form-delta feature used
a single fixed pair, `short=10, long=25`, not swept — Part 2 explicitly
did not ask for it to be, and Part 22 explicitly warns against
hyper-optimizing the exact lookback.

## D. Minimum-sample policy

**Full window required, no partial windows, no shrinkage.** A team needs
exactly `window` (or `long_window`, for form-delta) eligible prior games
this season, or the feature is `None` (DATA_UNAVAILABLE) — never a
partially-averaged 3-game or 8-game value presented as if mature. Chosen
as the simplest of Part 6's options, and the one least likely to
silently smuggle an unstable early-window number into the model.

## E. Season-boundary policy

**No cross-season carryover.** Every rolling window is season-scoped —
a team's prior-season games never count toward this season's window,
however strong or weak they were. A newly-started season requires
`window` games *within that season* before the feature matures again.
This is the simplest of Part 7's three options (closest to "A: reset to
league average," but stricter — `None` rather than a fabricated
league-average fill-in) and was chosen specifically so the temporal
reasoning stays trivial to audit; the tradeoff is lower early-season
coverage, reported honestly in Section K.

## F. xG integration formula

Part 11 option B: `p_candidate = sigmoid( logit(p_baseline) + beta·z )`,
where `z` is the STANDARDIZED (mean-0/std-1, fit on tuning data only)
`(home_feature - away_feature)` differential, and `beta` (or `beta_1,
beta_2` for the 2-feature Candidate E) is fit by plain batch gradient
descent minimizing mean log loss against **official NHL outcomes**
(never MoneyPuck's own goals), using only the 2023-24 tuning season's
mature-feature games. No neural network, gradient boosting, random
forest, or ensemble was used anywhere (Part 11's explicit prohibition) —
`research/xg_model_comparison.py::fit_logistic_weights()` is ~15 lines
of pure-Python gradient descent.

**Baseline definition — read plainly, not glossed over (Part 9 audit
finding)**: "the current production model unchanged" is specified to
include Elo, home advantage, season regression, the player PPG
heuristic, the goalie save% heuristic, rest/back-to-back, and the
uncertainty framework. The real NHL corpus has **no player, goalie, or
roster data** for these real games — only schedule/result.
`compute_probability_from_features()` is additive: with
`player_quality=0`, `goalie_adj=0`, `rest_adj=0` (the only honest values
absent real data for those signals), it collapses to **exactly**
`EloModel.win_probability()` — the same Elo-only baseline already
computed and validated in `ELO_REAL_DATA_COMPARISON_REPORT.md`. This
experiment reuses that exact, already-tested trajectory
(`research/elo_comparison.py::run_walkforward(games, weight_fn=None)`)
rather than recomputing it — Elo's own `update()` rule is never touched
anywhere in this experiment; MoneyPuck features only ever adjust the
*prediction*, exactly like player/goalie/rest features do in production.

## H. Tuning methodology

For every window in `{10, 25}` per feature family: standardize (mean/std
fit on that window's tuning-mature games only) → fit `beta` by gradient
descent on those same tuning-mature games → compute tuning-season Brier.
The window with the lowest tuning Brier is selected. This mirrors the
Elo experiment's precedent exactly.

## I. True evaluation methodology

**2022-23** = warm-up context for the baseline Elo trajectory only (this
feature family is season-scoped, so 2022-23 plays no role in the xG
features themselves — see Section E). **2023-24** = tuning/selection
(Section H), never touched again after selection. **2024-25 + 2025-26**
= true, untouched evaluation — no parameter (window, standardization
mean/std, beta) was ever fit using data from either season.

| Pair | Pearson r |
|---|---|
| 5v5 xG share (w25) vs. all-situation xG diff (w25) | **0.864** |

| all-situation xG diff (w25) vs. xG form delta (10/25) | 0.016 |

**B and C are highly redundant** (r=0.864) — both are LEVEL signals for
the same underlying team-strength concept, essentially the same
information viewed through slightly different situation/rate lenses.
The form-delta feature (D) is **essentially uncorrelated** with both
(r≈0.02) — it genuinely captures a different kind of information
(short-term trend vs. absolute level), exactly as the feature-family
design intended. Consequence: Candidate E was built from the
**least-correlated pair** (C + D, r=0.016), not B + D or B + C, per the
"favor simpler representative signals, don't stack near-duplicates"
instruction (Section G). This did not help — E performed worse than
either C or D alone, because it combines one candidate (C) that is
consistently harmful with one (D) that is directionally inconsistent.

## AA. Recommendation

```
KEEP CURRENT MODEL.
```

Checked against all 8 of Part 30's adoption conditions for the only
candidate that improved either metric (B):
1. Out-of-sample Brier improvement — **marginal pass** (-0.195%).
2. Out-of-sample log-loss improvement — **marginal pass** (-0.132%).
3. Improvement across both evaluation seasons — **fail**: 2024-25 is
   flat/negligible; the entire effect comes from 2025-26.
4. Acceptable calibration — **mixed/fail**: aggregate calibration error
   moved slightly worse; per-bucket picture is inconsistent.
5. No dangerous probability extremity — **caution**: +25-33% more
   extreme predictions than baseline, not dangerous but non-trivial.
6. Meaningful rather than microscopic effect — **fail**: sub-0.2%
   relative improvement on both metrics.
7. Clean temporal integrity — **pass**.
8. Enough feature coverage — **caution**: 68.8% of true-eval games,
   driven by the window-25 requirement and season-scoping policy.

B fails on effect size, season consistency, and calibration — three of
the eight required conditions — so it is not recommended for adoption,
despite being directionally the strongest single-feature result seen in
either this or the earlier Elo experiment (91%/88% of bootstrap
resamples favor it). C, D, and E are not close calls at all: all three
are aggregate *losses* against baseline. No candidate is recommended.

## AB. Recommended next single development slice

Two genuinely different, defensible options came out of this
experiment, and the choice between them is a scope/priority decision
rather than something the data settles on its own:

1. **Extend the xG feature family**, since the family showed a real
   (if inconclusive) signal and untested angles remain: opponent
   adjustment (explicitly deferred this slice, Part 8), score-adjusted
   xG (available, unused), or a shorter/tighter window grid to recover
   more of the coverage lost to the window-25 requirement.
2. **Move to the special-teams (5v4/4v5) feature family** now that team
   xG has been shown to carry *some* signal, per the original MoneyPuck
   roadmap ranking.

Given B's own result (real but inconclusive, undermined specifically by
coverage/season-consistency, not by the underlying signal being absent),
the more defensible next step is **narrowing rather than widening**:
retry the SAME 5v5 xG share feature with a tighter window (e.g. 10-15)
to recover coverage and test whether the signal survives with a larger,
more representative evaluation sample — before spending a new slice
opening up opponent-adjustment or special-teams complexity on an
already-inconclusive foundation.

## AC. Are we ready to begin a first visual dashboard?

**Not yet, and this experiment is itself part of why.** Every real-data
experiment so far (Elo real-data comparison, this xG experiment) has
concluded "keep the current model" — the production probability model
has not yet been improved by anything tested against real data. A
dashboard visualizing predictions from a model that real-data testing
hasn't yet validated as improved would risk presenting synthetic/
unvalidated confidence as more mature than it is. The honest state of
this project right now is: a temporally-correct, well-tested
architecture with a real Elo-only baseline that no tested enhancement
has yet beaten by a meaningful, robust margin. That's a legitimate,
useful checkpoint — but visual/dashboard work is more valuable once at
least one real improvement has cleared adoption, or once the project
explicitly decides the dashboard's purpose is showing the *research*
process itself (calibration curves, backtests) rather than a
"trust this number" prediction UI.
